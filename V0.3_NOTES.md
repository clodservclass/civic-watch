# CIVIC WATCH v0.3 — Data foundation

This release is **schema and read-only API infrastructure**, not live public-data ingestion.

## Deployment
1. Provision a PostgreSQL database separately, after approving any Railway charges. No database is automatically created by this PR.
2. Run `psql "$DATABASE_URL" -v ON_ERROR_STOP=1 -f migrations/0001_records.sql` against the selected database using an appropriately privileged migration role. Do not execute legacy `schema.sql` on the same database; it predates the new review-gated model.
3. Configure Railway service `DATABASE_URL` with a **read-only** DB user. Grant only `USAGE ON SCHEMA public` and `SELECT ON public_incidents, public_sources, schema_migrations`. Do not grant SELECT on private base tables or audit logs.
4. Check `/health` version 0.3.0, `/ready` returns ready, `/incidents` returns empty records initially, and `/demo/incidents` remains fictional.
5. Review release in GitHub before merging; Railway may deploy automatically from its configured branch.

## Privacy & publication
- New records default to `draft`, `unverified`, `sensitive=true`.
- Publication requires verified status, a reviewer identity and timestamp, non-sensitive classification, and at least one reviewed citation to appear in the public view.
- Public API never exposes internal notes, evidence storage keys, exact coordinates, or audit events.
- **Important:** the database constraints alone do not implement a secure moderation service. Reviewers must use a separately authenticated administrative process with audited updates before any real records are created or published.
- No real-time officer or enforcement movement data, public submissions, or evidence uploads.
- `/incidents` is empty until a database is connected and records are approved. The dashboard still uses the separate synthetic endpoint.

## API
- `GET /incidents?category=police&limit=25&offset=0`
- `GET /incidents/{uuid}` includes reviewed public sources
- `GET /ready` checks schema migration 0001
